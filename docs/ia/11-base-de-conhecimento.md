# Base documental SINDI

Projeto Supabase SINDI, região São Paulo, organização Atto Comunicação. Coletor Node no computador local; chat continua usando Ollama qwen2.5:1.5b. Nenhuma conversa é persistida nesta base.

`npm run knowledge:sync` faz uma varredura. `npm run knowledge:watch` mantém o processo ativo, aguardando 15 minutos depois de cada varredura. Sitemaps e páginas principais a cada ciclo; posts históricos diariamente ou quando lastmod sinaliza mudança. Não é tempo real: o site não fornece eventos. Uma varredura longa adia a próxima. O computador/internet precisam estar ativos.

Descoberta por sitemap e links internos; HTML visível com rodapé institucional; PDFs com texto até 25MB. Robots.txt consultado; domínios e redirecionamentos restritos; arquivos e textos têm limites operacionais. Falhas, imagens/PDFs sem texto, links externos, mídias e documentos maiores são pendências, não fatos confirmados. O sitemap possui aproximadamente 3.900 notícias: primeira indexação pode demorar. Conteúdo privado/login não é acessado. Não é possível prometer extração integral de imagens, vídeos, revistas externas e páginas ausentes do sitemap/links.

Hash SHA256 detecta alteração; ETag/Last-Modified evitam transferências desnecessárias quando suportados. URLs HTTP404/410 são retiradas da busca; falhas transitórias preservam última cópia, cuja data é indicada. Atualização de documento e trechos no Supabase é transacional; duas versões anteriores preservadas. Não inferir revogação jurídica só porque um link desapareceu. Publicação no site não implica vigência de CCT.

Tabelas sindi_documents, sindi_chunks, sindi_document_versions e sindi_sync_runs; busca textual PostgreSQL português com índice GIN e expansão simples de consultas PT/EN. Nesta versão não há embeddings nem busca semântica: paráfrases complexas podem não encontrar todos os documentos. Até quatro trechos por pergunta; no máximo dois por fonte; notícias ordenadas por publicação. Contexto relevante, datas e links enviados ao Ollama. Instruções exigem abstenção quando faltar evidência e tratam documentos como dados, não comandos. Isso reduz, mas não elimina, erros do modelo. Endereço é extraído diretamente da página oficial de contato, sem geração pelo modelo.

RLS em todas as tabelas. Leitura pública limitada a documentos oficiais ativos e seus trechos. Escrita/RPC de atualização, versões e relatórios somente service_role. Funções SECURITY INVOKER, search_path fixo; chaves secretas nunca NEXT_PUBLIC. A Publishable key é apenas leitura. Secret key fornecida pelo usuário por scripts/configure-knowledge.ps1, em .env.knowledge.local ignorado pelo Git; nunca imprimir seu conteúdo. O servidor lê configuração pública em .env.knowledge. Falha de Supabase usa espelho .data/knowledge/current.json. Relatórios locais em status.json; /base e /api/knowledge mostram apenas contadores/estado, sem segredos.

Para consultar situação: abrir /base. Para parar: Ctrl+C no coletor ou encerrar a tarefa SINDI-Knowledge, quando instalada. Uma única execução por lock de PID. Logs do coletor não contêm perguntas nem credenciais. Arquivos .data não devem ser publicados em hospedagem estática.

Antes de operação permanente: revisar amostras por tema/vigência, cobrir OCR/revistas externas prioritárias, testar perguntas PT/EN e casos sem fonte, monitorar espaço/limites do plano Free, testar reinício e definir responsável por revisão. Não há treinamento dos pesos do modelo nem garantia de ausência de alucinação.

Uma barreira lexical exige correspondência de pelo menos 70% dos termos relevantes com os trechos recuperados. Sem evidência suficiente, a resposta é de abstenção e não chama o modelo. Redação/tradução e saudações têm tratamento separado. Esse filtro favorece cautela: paráfrases podem gerar negativas mesmo com informação disponível. Ele não comprova que todos os detalhes da resposta estão sustentados; a revisão humana continua necessária.

Modo factual final: o Ollama recebe opções de trechos e retorna apenas IDs por schema JSON, com temperatura0 e geração limitada a64 tokens para a seleção (não é cota de mensagens). O servidor valida os IDs e monta a resposta usando exclusivamente texto literal coletado, fonte e data. Prosa/fatos/links gerados pelo modelo não são exibidos nesse modo. Relevância ou validade jurídica dos trechos ainda podem estar erradas; o sistema não assegura que um documento antigo seja vigente. Em English, apresentação/interface usam inglês, mas citações permanecem no idioma original para preservar fidelidade; tradução explícita usa o modo de redação. Redação/tradução livre continuam geradas pelo modelo e precisam de revisão. Perguntas sobre benefícios gerais priorizam a seção de associação coletada, distinguindo associada/filiada.

Tarefa Windows SINDI-Knowledge instalada para iniciar ao entrar na conta atual, com Node em janela oculta, sem privilégios administrativos. Executa também agora. Configuração não inicia automaticamente a aplicação Next/Ollama/túnel; manter esses componentes ativos para acessar o chat público. Após reiniciar é necessário entrar no Windows para disparar o coletor. Logs worker.log e worker-error.log em .data/knowledge. Para parar: Stop-ScheduledTask -TaskName SINDI-Knowledge. A task tem reinício em falha e bloqueio de instâncias duplicadas. Reinício físico do Windows ainda não foi testado.

Launcher final: scripts/start-knowledge.vbs pelo WScript do Windows, dando ao Node uma janela oculta independente dos terminais. Evitar Ctrl+C global ao reiniciar outros serviços; encerrar somente o PID identificado do serviço correspondente. Gravação do espelho usa substituição atômica com novas tentativas para EPERM/EACCES/EBUSY transitórios no Windows; aguarda todas as tarefas de coleta antes de sair após falha, sem deixar varreduras concorrentes. O helper PowerShell é alternativo, não a action da task final.

### Comportamento atual — 10/10/2026
As respostas agora são sínteses em linguagem natural. O modo anterior de exibir citações literais foi substituído por solicitação do usuário. As fontes são contexto para o modelo e referências ao final da resposta. Índices e alguns artefatos de PDF são filtrados antes da geração, inclusive nos registros existentes. Essa limpeza é heurística: não garante extração perfeita nem elimina a possibilidade de erro do modelo ao resumir.
